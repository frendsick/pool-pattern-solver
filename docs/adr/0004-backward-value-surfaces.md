# Backward value surfaces for onward control

Position Zones are gated on onward control computed by backward induction from the 9: for each ball k of a Layout, a value surface V_k rasterizes over the table (1.5″ grid, bilinear lookup) how good a cue position is for shooting ball k counting everything that still has to happen — pot of ball k discounted by onward control measured against V_{k+1}, down to the pot-only surface of the 9. The zone of ball k−1 gates against V_k, so the window drawn for the 7 already excludes spots from which the 8 is pottable but only into 8-on-9 dead positions. This replaces the previous one-ball-deep gate (zones of ball k+1 gated by the *pot-only* zones of ball k+2), which matched a player's thinking only two balls out; players plan position requirements from the last ball backward, and full racks (9 balls) make the difference material.

We rejected recursive on-demand gating (each `onwardControl` probing a gated next zone, recursively): the per-level fan-out of exit-line samples multiplies cost ~100× per ball of depth. The surfaces invert that — built once per Layout, last ball first, each level reading the previous as a grid lookup — and are pattern-independent, so the beam search, the landing-spread quadrature and the renderer all share them (`surfacesForLayout` cache). `bestNextValue` becomes a single array read instead of a loop of full zone evaluations, which made solving *faster* than before despite the deeper gate (full 9-ball rack ≈ 450 ms cold, surfaces ≈ 110 ms of that).

Each surface is normalized to its own peak before use as a gate target: chained values are products and shrink with rack depth, so the absolute CONTROL_SAT bar would drown the signal on long racks. The gate thus reads "can the cue ball reach a spot worth ≥ 60% of the best still available for the rest of the rack" — the same relative-to-best philosophy as ZONE_RELATIVE.

## Consequences

- The gate is a feasibility prior, not a maximizer: it saturates, so it must never *rank* near-tied candidates — only filter dead futures. Ranking the ball-in-hand placements by gated value regressed the side-hanger golden (the rigid straight-in stop placement outranked the angled placement that flows to the next ball, and the exact eNext search never saw the angled seed). `initialNodes` keeps pot-only ranking and uses the gate only to discard placements whose rest-of-rack value is zero.
- The reported score is untouched (ADR-0002): P(pot) factors stay pot-only, and the future is still measured exactly by the eNext chain; surfaces only shape which zones, bars and candidates the search and renderer see.
- Bilinear interpolation smears `zoneValue`'s hard zeros (ball shadows, clearance rings) by under a grid cell. The error enters only at gate depth ≥ 2 — the immediate next zone is always measured with exact `zoneValue` — so far-future requirements are coarse, which matches how fuzzy they really are.
- A dead surface (ball pottable from nowhere) gates the level above as "no gate" rather than zeroing it, so the failure surfaces at the dead ball's own zone targets, exactly where it did before.
- Surfaces depend only on Layout and forced ball order, so `generatePuzzle`'s solve-to-validate retries rebuild them per candidate layout — at ~110 ms per 9-ball build this is a real share of generation cost; coarsening the grid is the lever if generation ever needs to be faster.
